# Agent Note: 同一轮内的只读工具并发执行

Status: implemented

## Problem

主 Agent 与子 Agent 的提示词都要求模型把彼此独立的读取与检索放在同一轮发起，但循环内核按顺序逐个执行工具调用：一轮里的多次 `read_file` / `grep` / `glob` / `web_fetch` 耗时相加，模型并行发起也拿不到加速，联网抓取多个页面时尤其明显。

## Decision

- `run_agent_loop_ext` 把一轮中**连续的**、免审批的只读调用（`tool_risk == Read`，不含 `task`，不含无项目时需要路径授权的读取）合成一段并发执行：整段先下发全部 `tool_call` 事件，执行完成后按调用顺序下发 `tool_result` 并回填消息。
- 写入、命令、MCP、子 Agent 与需要审批的调用仍逐个执行，并作为并发段的边界：写操作之前的读取先完成，之后的读取等写入落地后再执行，同一轮内的读写先后关系不变。
- 并发执行放在 `spawn_blocking` 线程中，通过运行时句柄驱动异步工具：文件读取与检索是同步阻塞 IO，放进阻塞线程池才能真正并行，也不会占住异步工作线程。
- 并发段执行期间同样响应取消。
- 主 Agent 提示词把「可在同一轮并行发起」改为「应在同一轮一并发起」，引导模型合并独立读取。

## Alternatives considered

- 所有调用先统一审批再统一执行：用户会在看到前一步结果之前批准后一步，改变了审批语义，否决。
- 并发执行多个 `task` 子 Agent：子 Agent 共享并可变借用检查点，且可能发起审批，需要较大改造，本次不做。
- 直接 `tokio::spawn`：同步文件 IO 会阻塞异步工作线程，并发数超过核数时会拖慢 SSE 下发。

## Consequences

- 一轮多次独立读取的耗时从各次相加变为取最慢的一次；子 Agent 的调查同样受益。
- 前端会同时看到多张执行中的工具卡片，结果按 id 回填，无需改动。
- 用户取消时，已经派发的只读调用会在后台执行完毕后丢弃结果，不产生副作用。
