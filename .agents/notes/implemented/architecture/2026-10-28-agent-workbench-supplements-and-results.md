# Agent Note: Agent 工作台——补充要求、结果区与统一工具投影

Status: implemented

## Problem

- 运行中在输入框发送内容会先停止当前任务再发新消息，长任务里想补一句要求只能打断重来。
- 运行结束后只有改动列表与验证摘要，失败的命令、无法确认结果的操作、没送达的要求散落在折叠的过程里，也没有基于这些问题继续的入口。
- 侧栏是一条平铺的会话列表，只区分“运行中 / 等待确认”；失败、已停止、应用重启后被中断的任务看不出来，也看不出属于哪个项目。
- 工具结果在多个地方各自解析：成果面板认 `replace_file_content` / `terminal` / `TargetFile` 等网关并不存在的工具与参数，却漏掉了 `edit_file`；命令一律按 `isError` 显示成功或失败。
- 计划清单显示“所有计划步骤已完成”，运行结束后仍显示转圈的“进行中”，容易被当成执行结果。

## Decision

**补充要求（运行控制面 + 循环）。** `RunControl` 带一个 `SupplementQueue`。`POST /api/agent/runs/{runId}/supplements {id, text}` 入队（202）；运行不存在、已取消或正在收尾时返回 409（`RUN_NOT_ACTIVE` / `RUN_CANCELLING` / `RUN_FINISHING`），空文本或非法编号返回 400。同一编号重复提交只排队一次。

- 循环在每次调用模型之前取出补充：接在最后一条工具结果或用户消息末尾（“[用户在任务进行中补充的要求]”），上一条是助手回复时才新增用户消息，各家协议的交替约束不受影响；随后发出 `supplement_delivered {runId, ids}`。
- 模型给出最终回复时用 `close_if_empty` 原子地检查并关闭队列：仍有补充则保留这轮回复、带着补充再走一轮；关闭后到达的补充被拒绝。运行以其他方式结束时执行任务关闭队列。因此不存在“已接受却永远不送达”的补充。
- 前端：Agent 运行中（消息带运行身份、未在取消）输入框回车即追加补充，停止按钮同时保留；普通对话仍是停止后发送。补充记录在 assistant 消息的 `supplements` 中：排队中 → 已送达（收到事件）→ 运行结束仍未送达或被网关拒绝则为未送达，可“作为新消息发送”。已送达的补充在之后的请求历史中并入触发该运行的用户消息。

**结果区（`domain/run-result.ts` + `RunResultSummary`）。** 只依据执行记录列出未解决的问题：同一命令最后一次失败、超时或未能确认退出；同一文件最后一次写入失败；运行结束时没有结果的操作与取消收尾时无法确认的外部调用；未送达的补充。模型回复中的“已修复 / 已通过”不消除条目。最新一条回复提供“继续处理这些问题”，把问题清单作为新消息发给同一会话（不动输入框里的草稿）。改动汇总（运行账本）与验证摘要保持原样，位于其上方。

**统一工具投影（`domain/tool-projection.ts`）。** 工具类别只来自网关实际提供的工具名；路径统一分隔符；命令结论以结构化记录为准（`commandStatus` 移到这里，`verification.ts` 复用）；没有结果的步骤在运行中为 running，消息结束后为结果未知。改动汇总、验证摘要、结果区与成果面板都用它；成果面板补上 `edit_file`，删除不存在的工具分支，命令卡显示退出码与结束原因，文件卡的“查看改动”直接打开所属运行的审阅。权限卡也删除了 `replace_file_content` / `TargetFile` 分支。

**侧栏。** 有会话绑定项目时按项目分组（组序取组内最靠前的会话，未绑定项目的放最后），组头显示运行中数量。实时状态新增“正在取消”“等待写入”（`run_status: waiting_for_workspace`，此前前端会把该事件当成流损坏）。会话记录 `lastRun`（随带运行身份的 assistant 消息写入，撤回或删除时回落），没有活跃运行时显示最近一次运行的结局：失败、已停止，仍记为运行中的显示“已中断”。

**网页版的能力边界。** 网页版（非桌面运行时）不显示无法生效的项目选择与执行模式入口；空白会话的输入框上方，以及右侧“代码审阅”“工作区”页，说明网页版只提供对话、附件与联网搜索，读写项目文件、运行命令、审阅与撤销改动需要桌面版。已有对话功能不受影响。

**计划与结果分开。** 计划条标为“计划进度”，全部完成时只说“计划步骤均已标记完成”；运行结束后“进行中”的步骤显示为“停在：…/未完成”，展开后注明验证结论以命令执行记录为准。

## Alternatives considered

- 补充要求直接作为新的用户消息发起第二个运行：会与仍在执行的运行并发写同一项目，且模型看不到它正在做的事情。
- 在网关收到补充时立即插入消息列表：循环正在等待模型或执行工具时修改消息会打乱工具调用配对；只在调用模型之前送达才安全。
- 运行结束后仍静默接受补充并在下次运行带上：用户看不到它是否生效；拒绝并标记未送达更诚实。
- 侧栏状态全部靠加载消息推断：侧栏不加载消息；把最近一次运行的状态写在会话记录上，代价是一次额外的字段更新。

## Consequences

- 补充要求送达后模型会在同一运行中继续，最终回复可能在已显示的回复之后继续增长。
- `lastRun` 只记录前端持久化过的状态；应用重启后的“已中断”指前端没有活跃运行，网关是否仍在执行由阶段五的重连处理。
- 时间线沿用消息内按事件顺序排列的过程视图，没有另建组件。
