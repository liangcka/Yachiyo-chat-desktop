# Agent Note: 消息事件顺序与桌面对话布局

Status: implemented

## Problem

消息分别聚合正文、思考与工具步骤时，展示层无法区分工具执行前后的正文。固定将工具置顶会让授权说明出现在执行结果之后。桌面对话同时存在外层卡片、顶栏控制和输入区控制，挤占正文空间。

## Decision

- `ChatMessage.contentSegments` 保存正文、思考和工具调用的到达顺序。正文与思考使用现有字符串的 UTF-16 起止偏移，工具使用调用 ID，不重复保存全文或工具输出。
- 流式缓冲仅合并相邻同类增量，在工具调用前提交待处理增量。界面投影、定时持久化，以及完成、停止、失败三个终态都携带顺序快照。
- 思考片段的耗时从首个思考增量到下一类内容事件或终态计算。连续思考增量合并为同一片段；后续工具与正文耗时不计入该片段。
- 展示层按片段顺序渲染，只有相邻工具调用合并为一条折叠摘要。成功结果不展示完成徽标，失败在摘要与明细中提示。
- 缺少顺序字段的旧记录按思考、工具、正文展示；缺少计时数据时使用“查看思考”。存储索引和数据库版本保持现有契约。
- 桌面侧栏、对话区和成果区采用分割线布局。项目、模式、联网、技能、模型与成果入口集中到输入区；消息操作在末尾悬停或键盘聚焦时显示。欢迎页使用本地用户名与时间问候，建议入口采用输入框下方的小标签。

## Alternatives considered

- 只调整工具、思考、正文三个固定区块的顺序：无法表达多轮工具调用之间的正文。
- 为每个事件重复保存完整正文或思考：增加流式快照和本地存储开销。
- 替换原有 `text`、`thought`、`toolSteps`：扩大请求历史、复制功能与已有存储的迁移范围。
- 根据旧正文内容推测工具位置和思考耗时：缺少可靠数据，无法保证还原结果。

## Consequences

新回复在流式阶段和重新打开会话后保持相同的内容顺序。复制正文及生成请求历史仍读取原有聚合字段。旧消息的真实交错顺序无法恢复，思考耗时也不包含首个思考增量到达前的服务端等待时间。
