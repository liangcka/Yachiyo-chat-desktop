# Agent Note: 断线重连与运行恢复

Status: implemented

## Problem

- 运行的生命周期绑在 SSE 连接上：连接断开（窗口刷新、网关连接抖动、开发时热重载）就置位取消标志，长任务被意外终止；前端也无法重新连上仍在执行的运行。
- 事件没有编号，重连后无法知道从哪里继续，也无法去重。
- 前端只把存储里残留的“运行中”消息一律改成“已停止”，分不清运行其实已经完成、失败、被取消、随进程退出，还是根本无法确认；残留消息里的写入操作是否生效也没有提示。

## Decision

**运行与连接解耦。** 每个运行的 `RunControl` 带一份事件日志（`run_events.rs`）：执行循环产生的事件编码后按序号（从 1 开始）写入，终止事件（done / error）由执行任务写入后结束日志。`/api/chat` 的 SSE 只是日志的订阅者，从序号 0 读起、空闲时补发心跳；连接断开不影响运行。取消只走显式取消接口。

- `GET /api/agent/runs/{runId}/events?after=N`：从 N 之后回填并继续推送，运行结束且读完后关闭。每个事件带 `id: <序号>`。日志超过 2 万条或 16 MiB 时丢弃最早的事件，回填区间被裁掉时先发 `event: gap`。
- 运行结束后日志在内存中保留（最多 16 个运行、30 分钟），断线的客户端仍可回填最后的事件。
- `GET /api/agent/runs/{runId}`：`active`（附最后序号）或 `finished`（结局、原因、最后序号、事件是否仍可回填）；没有任何记录时 404。

**最小运行记录（`run_records.rs`）。** 运行开始与结束时各写一次 `run-records/<runId>.json`（与密钥文件同目录，原子改名写入，最多保留 300 份）：编号、会话、工作区、开始/结束时间、结局（running / completed / failed / cancelled）、原因、最后序号。不保存对话内容。当前进程里不活跃却仍记为 running 的记录报告为 `interrupted`（进程在运行结束前退出）。

**前端重连。** 事件处理完后记录序号（`ActiveRun.lastSeq`，随部分持久化写入 `ChatMessage.runEventSeq`）。连接层面的中断（网络错误、流在终止事件之前结束、空闲超时）且运行已确认时，按 `lastSeq` 重新连接（间隔 0.3/1/2/4/8 秒），期间消息显示“正在重新连接”；回填的重复事件按序号跳过。网关下发的错误事件不是断线，不重连。日志已不可用时依据运行状态收尾；始终连不上网关则标记结果未知。

**启动与切换会话时的恢复。** 存储中仍为“运行中”的 Agent 消息先按已停止显示、存储保持原状，再向网关确认：

- 运行仍在执行或刚结束且日志仍在：重新连接并从序号 0 回放，重建这条消息（包括仍在等待的审批卡），之后与普通运行一致；启动时还会列出网关中的活跃运行，在后台接回其他会话的运行。
- 日志不可用：按运行记录标记 `recovery`——已完成但最后的输出没有接收到、失败、已取消、被中断或未知——并落盘。

**恢复入口（`RunRecoveryNotice`）。** 说明结局并列出未确认结果的操作（没有返回结果的工具调用、未能确认退出的命令、取消收尾时无法确认的外部调用），明确“不会自动重放”：

- 查看改动：打开该运行的任务审阅（阶段三的运行账本），据实际文件状态处理。
- 继续任务：以新消息发给同一会话，附上未确认的操作，要求 Agent 先核实当前状态再继续，不得假设它们已执行或未执行。
- 重新尝试：重新生成这条回复；存在可能有副作用的未确认操作时先弹出确认，说明可能重复写入、已改动的文件不会自动撤销。

## Alternatives considered

- 保留“断开即取消”，只在前端避免断开：窗口刷新与网关连接抖动无法避免，长任务会被白白终止。
- 重连时只依赖前端持久化的部分消息并从 `runEventSeq` 继续：审批请求等事件可能早于持久化的序号，接回后审批卡丢失、运行一直等到审批超时；从 0 回放才能完整重建。
- 把完整事件日志落盘：恢复只需要结局与“是否还能回填”，对话内容已由前端持久化；落盘日志会带来体积与隐私成本。
- 恢复后自动重新执行未确认的操作：无法区分操作已生效还是未执行，自动重放可能重复写入或重复调用外部服务。

## Consequences

- 关闭窗口不再取消运行（应用进程退出时运行随之终止并记为被中断）；需要停止时必须使用停止按钮。
- 事件日志常驻内存直到运行结束后被淘汰，单个运行最多约 16 MiB。
- 回放从 0 开始时，前端以回放结果替换残留消息；日志被裁剪过时消息会缺少最早的过程并标注“部分过程未能回填”。
