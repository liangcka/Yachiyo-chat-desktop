# Agent Note: 长任务的上下文预算与交付前执行反馈

Status: implemented

## Problem

- Agent 循环只对单个工具结果做截断，以及把较早轮次的只读输出折叠成一句话；没有整体预算。长任务的写入、命令与助手说明持续累积，最终由上游返回上下文超限错误，运行以失败结束。
- 一旦需要压缩，简单丢弃旧消息会拆散工具调用与结果的配对（多数厂商直接拒绝），也会丢掉目标、用户中途补充的要求、改过的文件与出现过的失败。
- 压缩、超限、循环叫停与输出截断中，前两者在界面上完全不可见。
- 模型常在改完代码后不验证就宣布完成，或在验证失败后仍声称通过；提示词只说“出错就修复”，循环没有任何反馈。

## Decision

**上下文预算（`context_budget.rs`）。** 请求带上模型窗口（`agent.contextWindow`，来自自定义模型设置；缺省按 64k 保守估算）。预算 = 窗口 − 输出预留（窗口四分之一，最多 16k）− 系统提示词与工具定义。token 按 UTF-8 字节数的三分之一粗估（宁可早折叠）。每次调用模型前，对裁剪后的实际发送内容估算：

- 未超出：不改动。
- 超出：从本次运行最早的一轮开始整轮折叠（助手消息连同其全部工具结果与附图一起移除），直到放得下；最近两轮始终原样保留，包括厂商原生输出与思维链。本次运行之前的对话历史由客户端管理，不在折叠范围内。
- 折叠的内容写进【运行进展摘要】，附在本次请求原文之后：用户在任务进行中补充的要求（送达时即登记，折叠后不丢）、已修改的文件、出现过的失败（工具与输出首行）、按顺序的操作及结论、此前的说明。摘要明确它来自实际执行记录，需要细节时应重新读取。
- 已无可折叠的轮次仍超出：保留轮次中除最后一轮外的长工具结果只留首尾；仍放不下则发出 `run_note: context_overflow` 并以 `done.reason = "context_overflow"` 停止，不把超限请求发给上游。

**交付前执行反馈（`delivery_check.rs`）。** 循环登记每个工具结果：成功写入源代码文件（按扩展名，文档与说明不算）记为“修改后未验证”；按与界面一致的规则识别验证命令（测试、构建、类型检查、静态检查，以及在命令开头执行的项目测试/检查脚本，如 AGENTS.md 里约定的 `sh test.sh`），以网关的结构化结果判定通过与否（被停止或未确认退出的不算结论）。模型给出最终回复时：

- 修改了代码且之后没有验证：提醒一次，列出文件，要求运行验证或在总结中说明原因与风险；
- 最近一次验证失败：提醒一次，要求修复后重验，无法修复时如实说明，不得声称通过。

提醒以用户消息追加在这轮回复之后（交替约束不受影响），循环继续；每种提醒一次运行最多一次。提示词同步写明“取证 → 修改 → 验证 → 处理失败 → 交付”的顺序与总结应包含的内容（改了什么、验证及结果、未解决的问题）。

**界面可见。** 新事件 `run_note {kind, detail}`：`context_compacted`（折叠轮数、前后估算）、`context_overflow`、`verification_reminder`（原因与文件或命令）。记录在消息的 `runNotes` 中并持久化，消息下方以“运行提示”列出；上下文超限停止时按完成落盘（已执行的步骤仍有价值），最新回复提供“继续任务”。循环叫停与输出截断沿用原有的说明。

## Alternatives considered

- 让模型自己写摘要再继续：额外一次模型调用的成本与延迟，摘要还可能遗漏失败与约束；执行记录本身就足以写出确定性的摘要。
- 按消息条数或固定字符数裁剪：与模型窗口无关，小窗口仍会溢出、大窗口白白丢上下文。
- 每次结束都强制要求验证：文档类修改与无法验证的环境会陷入循环；只对源代码修改、每种提醒一次。
- 用精确分词器计算 token：各厂商分词不同，依赖额外的模型资源；保守估算加整轮折叠已能避免溢出。

## Consequences

- 被折叠的轮次在本次运行中只剩摘要；模型需要细节时会重新读取文件或运行命令。
- 估算偏保守，英文为主的内容会比实际更早折叠。
- 交付前提醒会让循环多走一轮，界面上同一条回复可能在“看似完成”之后继续增长。
- 子 Agent 不做预算（运行很短，且只回传报告）。
