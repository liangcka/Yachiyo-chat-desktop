# Agent Note: 任务级改动审阅与安全撤销

Status: implemented

## Problem

- 右侧“代码审阅”以 Git HEAD 为基线。任务开始前用户已有的未提交改动、未跟踪文件也显示成 Agent 的改动；“应用采纳”用 HEAD 原文加上已采纳块整体写回，未处理的块和用户原有的修改都会被回退。
- 只认 `write_file` / `edit_file` 的参数路径，命令（脚手架、格式化、`mv`、`npm install` 写锁文件）产生的改动既不显示也无法撤销。
- 界面写入（编辑器保存、审阅写回）不核对磁盘版本：Agent 或命令在审阅期间改过的文件会被旧内容盲目覆盖；`read_file` 超过 2000 行时返回带行号的分页文本，保存会写坏文件；BOM、CRLF 与非 UTF-8 编码在保存时丢失。
- 同一项目里并发的两个运行各自写文件、各自做检查点，无法区分改动归属。

## Decision

**运行改动账本（`gateway/agent/changes.rs`）。** 每个运行一份账本，存放在检查点存储下 `runs/<runId>/ledger.json`，内容按摘要存入 `blobs/`。条目记录路径、改动前版本（baseline）、运行最后写入的版本（agent）、来源（file_tool / command）、相关调用与用户处理过的版本（reviewed）。

- 基线是“本次运行第一次改动该文件之前”的内容：文件工具在写入前读取原文；命令与 MCP 在执行前后各做一次元数据指纹（大小、修改时间、是否存在），变化的路径取本轮检查点中的内容作为基线。任务开始前已有的改动因此留在基线里，不算本次改动。
- 状态由当前文件版本推出，不另存：等于 agent 为待处理，等于 baseline 为已撤销，等于 reviewed 为已处理，其余为冲突（写入后又被用户或其他运行改过）。冲突文件不能直接撤销。
- 记录失败不吞掉：工具结果末尾追加“改动跟踪失败”，模型与界面都能看到。

**写入协调。** `WorkspaceManager::write_lock(root)` 为每个工作区提供一把异步锁，写文件、执行命令与 MCP 调用期间持有，只读工具不受限。同一项目中的并发运行轮流执行有副作用的操作，指纹窗口内只有自己的改动，归属可证明正确；等待时发出 `run_status: waiting_for_workspace`。不迁移用户工作区，不引入 worktree。

**版本化界面写入（`tools/versioned.rs`）。** `read_workspace_file` 返回完整原文、版本摘要、是否 UTF-8 无损与是否带 BOM；`write_workspace_file` 必须带上读取时的摘要，不一致时返回 `FILE_VERSION_CONFLICT` 且不写入；覆盖前把旧内容存入 `ui-backups`（每个工作区最多 200 份，可列出与恢复，恢复同样核对版本）。写入保留 BOM 与原换行；非 UTF-8 文件只读打开。IPC 的 `read_file` 固定返回原文，不再分页加行号。

**撤销与保留。** 界面只提供“保留 / 撤销”，不再有“采纳后写回”：

- 按块撤销：前端以 `structuredPatch(baseline, current)` 编号，选中的块做 `reversePatch` 后套用到当前内容；补丁无法套用时报错，不退回整体覆盖。未选择的块保持现状。
- 整个文件撤销恢复基线（新建的文件被删除、删除的文件被恢复）；保留只记录 reviewed 版本，不写文件。撤销后可以“恢复 Agent 版本”。
- 所有操作都携带界面看到的当前摘要，并取工作区独占租约（运行中的项目会被拒绝）。
- “撤销全部待处理”先逐个核对版本与冲突，任何一个不满足就一个都不写；然后按“修改 → 删除 → 新增”的顺序恢复，重命名的旧路径先回到原位再删除新路径。写入中途因并发修改失败时，错误中列出已撤销与未处理的文件。

**界面。**

- 右侧“代码审阅”分为“本次任务”（`TaskReviewPanel`，按运行显示账本改动，可切换会话中的其他任务，显示运行所属项目）与“工作区 Git”（`DiffReviewPanel`，相对 HEAD 的只读差异，说明其中包含任务开始前的改动）。
- 消息下方的改动汇总优先读取运行账本，包含命令产生的改动与已撤销、冲突等状态；“查看改动”直接打开该运行的审阅。没有账本记录的旧消息退回到文件工具参数中的路径。
- 编辑器标签以“工作区 + 路径”为身份，保存时核对版本；冲突时标记并要求重新加载。撤销、保存、恢复检查点后广播 `workspace-events`：未修改的标签自动重新加载，有未保存修改的标签标记冲突；文件树只重新列出受影响的已加载目录；审阅面板与改动汇总重新读取。

## Alternatives considered

- 继续以 HEAD 为基线，只在写回时跳过未处理的块：仍无法区分用户原有改动与 Agent 改动，撤销“整个文件”时会回退用户的工作。
- 每次写入都做全量内容快照来归属命令改动：大项目开销过高；元数据指纹定位变化路径，再从本轮检查点取内容即可。
- 并发运行各自使用 git worktree：需要迁移用户的未提交改动，与“不得迁移用户工作区”冲突；写入锁是能证明归属正确的最小协调。
- 撤销时直接覆盖当前内容：审阅期间文件可能已被修改，必须以版本摘要为前提。

## Consequences

- 两个运行在同一项目中只能轮流执行写文件与命令；长命令会让另一运行的写操作等待（界面显示等待原因）。
- 命令改动按元数据判断：同一秒内大小不变的改写理论上可能漏检；检查点排除的目录（`node_modules`、`.git`、构建产物等）与超过上限的大文件不进入账本。
- 检查点恢复仍是整个工作区的回滚，可能覆盖其他运行的改动；恢复后账本状态会显示为已撤销或冲突。
- 非 UTF-8 文本只能整体撤销；二进制文件只记录存在与摘要。
